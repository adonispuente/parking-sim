# Parking-sim game plan — 2026-11-09

Author: CLAUD (strategist). Status: proposed, awaiting Commander approval. No code changed in this pass.

## Position (two sentences)
Make the simulation's *timing* match a real Sunday before adding new actors, because every later feature (in-lot positions, crosswalks, walkers) reacts to when people leave. Then turn the existing positions registry into a plug-in system and add the crosswalk as its first new position, so pedestrians arrive as a position-controlled flow instead of a separate subsystem.

## The decision (1-3-1)
**Question:** In what order do we build Lot A/departures, the position system, and pedestrians?

1. **As listed** (A rule -> positions -> pedestrians). Fast first win, but pedestrians get built on whatever position plumbing exists, and the B-gate conflict stays unresolved.
2. **Foundation first** (position framework -> everything). Cleanest architecture, but a long stretch before any visible behavior change, and the framework gets designed without a real second use case.
3. **Realism first** (timing -> position framework with crosswalk as its first plug-in -> walkers/shuttle riders). Each milestone ships visible behavior, and the framework is designed against a concrete new position.

**Recommendation: option 3.** Timing is the input everything else depends on, it is the smallest change, and the crosswalk is the natural first test of the position system.

## Ranked milestones
Ranked by value per hour of the Commander's time. Owners follow the standing roles: SPARTAN plans/verifies, CLAUD does code planning and larger changes, QWEN does bounded tasks.

### M0 — Trustworthy test baseline (prerequisite, ~0 Commander time)
- Classify and fix or retire the 27 legacy failures so every later milestone has a clean pass/fail gate.
- Owner: QWEN triage (already queued) -> CLAUD fixes real bugs -> SPARTAN verifies.
- **Gate:** full suite 100% pass, or each remaining failure marked obsolete with evidence and removed.

### M1 — Real departure timing + Lot A rule (highest leverage)
All in `sundayServices.js` plus tests:
1. Let-out = start + 75 min, as a named constant.
2. Departure curve: **~5% early** (5-10 min before let-out), bulk after let-out, **~2% linger**. Replace the 15%/35-min defaults.
3. Start each transition sim **10 min before** the previous let-out so early leavers are in the run. Re-check the hard-coded 20-min "early stream" (`clock<1200`) against the new start.
4. Fix the 1:15 sim start so it begins at (or 10 min before) 12:15.
5. Lot A gate: reopen only when **clock >= let-out AND general A <= 50%**. Early leavers never reopen A.
6. Lot B gate: resolve per the Commander's answer below.
- Owner: CLAUD code, QWEN timing tests, SPARTAN 11:00 and 1:15 comparison runs.
- **Gate:** tests prove A stays closed before let-out even below 50%; measured early-leaver share 4-6%, linger share 1-3%; departures, shuttle circuits and routing errors compared against the current 11:00 baseline (760 departures in 40 min).

### M2 — Position plug-in system
The registry already records duty/implemented/intended. What is missing is a cheap way to *add* one.
1. Decouple new positions from the 65-shape loader: an additive overlay file for points drawn after the Clear Image, with provenance, so adding a position never renumbers or rebinds the source.
2. One controller contract by kind: `controller` (holds/admits traffic), `checkpoint` (route must pass), `radio` (shares state), `visual`. One hook signature for hold/admit, one for radio state.
3. Port one existing controller (e.g., Lot B north exit) onto the contract with no behavior change.
4. Sunday Operations lists each position and its kind.
- Owner: CLAUD design + port, QWEN registry tests, SPARTAN no-regression run.
- **Gate:** adding a dummy position is one overlay entry + one definition, no loader edit; the ported controller gives identical 11:00 results.

### M3 — Crosswalk as the first new position
- Crosswalk = a `controller` position that holds vehicle lanes while a pedestrian batch crosses. Start with **timed batches** (aggregate flow), not individual walkers.
- Owner: CLAUD, SPARTAN verifies car-throughput impact.
- **Gate:** hold visible in the scene; measured car delay per crossing; no gridlock in a 40-min 11:00 run.

### M4 — People: walkers and shuttle riders
- Each car carries N people; at let-out they split into **walkers** and **shuttle riders**. Shuttles board up to **20**; riders queue at stops; walkers feed the crosswalk(s).
- Individual pedestrian agents only if aggregate flow cannot answer the Commander's questions.
- **Gate:** shuttle load factor and stop queue length reported per circuit; walker volume drives crosswalk holds.

### M5 — In-lot positions (ongoing)
- Add positions inside each lot (row-fill marshals; inside-Bravo marshal is already listed as "intended") one at a time on the M2 system.

## Riskiest assumption and the cheapest test
- **Assumption:** the departure shape (5% early, bulk at let-out, 2% linger) is close enough to reality that tuning cars and positions against it is meaningful. If it is off, every later milestone is tuned to the wrong surge.
- **Kill-test (one Sunday, no code):** at the 9:00 let-out, note when Lot A drops to about half full, and roughly how many cars are gone by let-out +10 and +20 min. Compare with M1's simulation. If the real half-full time differs by more than ~5 min, recalibrate M1 before M2.
- **Second assumption:** pedestrians matter mostly as crosswalk holds on car traffic, not as individuals. **Kill-test:** count people per crosswalk cycle at let-out once. If crossings are continuous rather than batched, M3 needs a continuous-flow model.

## What would change this plan
- Kill-test shows timing already close: shrink M1 to the Lot A rule only and move to M2.
- Crosswalks are unstaffed signals: M3 becomes a control point (like the Equity/Clay stop), not a staffed position; order unchanged.
